# ssb_mic_test.ino — Serial Command Reference

Send any of these single characters over the serial monitor (921600 baud). Each command prints a `->` confirmation line showing the new state.

## Signal source

| Key | Effect |
|---|---|
| `t` | Two-tone test signal (700/1900Hz by default) |
| `s` | Single clean tone (1000Hz) — isolates DSP/RF chain from mic-side artifacts |
| `m` | Live mic input |
| `p` | Envelope step test — 4Hz square wave direct to PWM, carrier held fixed. For measuring the analog reconstruction filter's step response with a scope, independent of everything else in the chain |
| `y` | FM isolation test — pure sinusoidal frequency modulation (1200Hz mod, 3000Hz peak deviation), envelope held fixed, bypasses `ssb_dsp_process_sample()` entirely. Isolates the AD9851/SPI/delay-line chain from the Hilbert/DSP math |
| `h` | AM isolation test — pure sinusoidal amplitude modulation (1200Hz mod, 100% depth), `freq_dev_hz` locked at 0, also bypasses `ssb_dsp_process_sample()`. Isolates the RSET/PWM/analog-filter/transistor path |
| `w` | Sine-chirp test — logarithmic 20Hz–20kHz sweep over 5s direct to the envelope/PWM output, with a synced square-wave reference on pin13 and a 30ms mute/sync marker at each restart. See "Sine-chirp test mode" below |
| `T` | Steps the two-tone pair through `TWOTONE_BAND_PRESETS` (`test_signals.cpp`), low to high center frequency: 300/500, 700/900, 1500/1700, 2500/2700, 3500/3700Hz (all 200Hz spacing, each a clean single-point probe), then the original 700/1900Hz pair (1200Hz spacing, kept last for reference — its wide spacing averages alignment across a much bigger span, so it's not directly comparable to the other five), wrapping around. Switches into two-tone mode too if not already there. For sweeping the pair across the audio band without a recompile, to empirically map how much relative-delay retuning each band needs — see the group-delay-equalizer band-mapping note below |

### Sine-chirp test mode (`w`, `AUDIO_SRC_CHIRP`)

Added to characterize the envelope/PWM (RSET) analog reconstruction filter's transfer function against a 2-channel ADC-based TF measurement rig, replacing the need to infer the filter's shape indirectly from two-tone/step-response artifacts.

`w` starts a logarithmic sweep from `CHIRP_F0_HZ` (20Hz) to `CHIRP_F1_HZ` (20kHz) over `CHIRP_SWEEP_SEC` (5s), direct to the envelope/PWM output, repeating continuously. A `CHIRP_MUTE_SEC` (30ms) silence at the start of every repeat acts as a sync/restart marker the measurement rig can trigger on. A square-wave reference — high while the chirp's own instantaneous sine is ≥0, forced low during the mute period — is driven on `CHIRP_REF_GPIO` (pin39, moved from pin13 2026-09-02 — see the GPIO13 section below) for the rig's reference channel. All constants live in `config.h`.

Unlike `p`/`y`/`h` (which bypass only `ssb_dsp_process_sample()` and still run on the normal `SAMPLE_RATE_HZ` (16kHz) full-tick pipeline), chirp mode bypasses ADC, DSP, `envelope_floor`, relative delay, AD9851, and normal diagnostics, and runs on **every** fast tick, i.e. the full `ENVELOPE_INTERP_FACTOR x SAMPLE_RATE_HZ` (64kHz) rate `envelope_interp.h`'s fast-tick timer already runs unconditionally at. This is required, not a convenience: 16kHz's own 8kHz Nyquist can't represent a 20kHz sweep.

**DC operating point — `u`/`j`/`i`/`k`/`D` still apply, master gain does not.** The offset/scale mapping (or predistort LUT if `D` is on) is deliberately the one pipeline stage chirp mode does NOT skip — every other bypassed stage would corrupt or be irrelevant to the raw filter TF, but this one sets WHERE on the duty range the sweep sits, which is exactly what you need to sweep to characterize the filter/BS170 gate across different bias points (e.g. testing whether the TF changes at the low vs. high end of the duty range). Master gain (`+`/`-`) does NOT do this — it only scales the swing depth around `AM_TEST_DEPTH`'s fixed mean (same convention `AMTEST` uses), so it changes how hard the filter is driven without moving the DC point at all; seeing no TF change between high/low gain is the expected result, not a null finding. Use `u`/`j` to shift the range and `i`/`k` to widen/narrow it instead.

**2026-09-02, reported and fixed: the `'w'` reply's own `serial_reply()` buffer was too small.** Adding the `'g'` state to the `'w'` confirmation text pushed that one reply to ~500 bytes, well past `serial_reply()`'s internal `char buf[256]` — `vsnprintf()` silently truncated it, which is exactly why the trailing `\r\n` went missing (the truncation cut it off) rather than anything electrical or timing-related. Fixed two ways: bumped the buffer to 512 bytes (comfortable headroom over every current reply in the file) and added a `Serial.printf()` warning on any future truncation, so it can't go silently unnoticed again the way this one did. Also trimmed the `'w'` reply text itself down to ~216 bytes for margin. The reported follow-on symptom ("second w gives no response") was initially explained away as the same pre-existing `src != TARGET` guard every other source-switch command uses (`t`/`s`/`m`/`p`/`y`/`h`) - technically correct, but the wrong call for `'w'` specifically. Reconsidered once the user pushed back: `'w'`'s own comment already documents that it's supposed to restart the sweep from t=0 on every press, and the new `'g'`-toggle A/B workflow gives a real, concrete reason to actually want that while already mid-sweep - without a restart, toggling `'g'` leaves you waiting up to the full `CHIRP_SWEEP_SEC` (5s) for the next natural mute/sync marker instead of an immediate, cleanly-triggered restart. **Fixed by dropping the guard for `'w'` specifically** (`c == 'w'` instead of `c == 'w' && src != AUDIO_SRC_CHIRP`) - it's now the one source-switch command in the file where re-sending it while already in that mode is a deliberate, useful "restart now" action rather than a no-op, and the code comments explain why it's an intentional exception to the rest of the file's convention rather than an inconsistency.

**2026-09-02, `g` (group-delay equalizer) now also applies, on request — to directly measure how well `envelope_gdeq` compensates the analog filter's group delay, not just characterize the raw filter.** `envelope_gdeq_process()` is called on `chirp_envelope` right after `test_signals_generate_chirp()`, before the offset/scale/predistort mapping — same insertion order as the normal pipeline. It shares the same live `'g'` toggle as everything else (the function internally no-ops when disabled, so no separate gating was needed), so the workflow is: sweep with `g` off for the baseline/uncompensated TF, toggle `g`, re-run `w` for the compensated sweep, and compare group delay (phase slope vs frequency) between the two on the TF rig. The `'w'` serial reply now reports current `g` state so it's visible at a glance which sweep is running. `envelope_floor` stays skipped — it's a hard near-zero clamp for mic-path silence, not something relevant to measure through.

**pin conflict**: `CHIRP_REF_GPIO` reuses the same physical pin as `TIMING_DEBUG_GPIO_CMD` (the serial-activity-correlation marker toggled every `loop()` iteration — see `config.h`'s `TIMING_DEBUG_GPIO_CMD`/`ADC_ISR_DEBUG_PIN_ENABLED` history). `CMD_DEBUG_PIN_ENABLED` (config.h, default **0**) gates that marker off so chirp's reference square wave isn't corrupted by it; flip it back to 1 (and expect chirp's reference output to go dark) if that marker is needed again instead.

## Phase/envelope relative timing

| Key | Effect |
|---|---|
| `[` | Decrease relative delay by 0.05 samples (5µs) |
| `]` | Increase relative delay by 0.05 samples (5µs) |

Signed, bipolar, fractional (interpolated between ring-buffer samples). **Positive** delays the *phase* path (AD9851) relative to envelope. **Negative** delays the *envelope* path relative to phase. Range roughly ±6 samples. Current best-known value: **-0.20 to -0.25 samples**.

## PWM duty-cycle range (envelope → RSET mapping)

Separate from master gain — this only remaps envelope's own output into a duty-cycle range, controlling where the signal sits relative to the BS170 gate's characterized sweet spot (~2.3V ±0.75V).

| Key | Effect |
|---|---|
| `u` | Raise duty range offset by 2% |
| `j` | Lower duty range offset by 2% |
| `i` | Widen duty range span by 2% |
| `k` | Narrow duty range span by 2% |

Default: offset 0.20, scale 0.90 → duty range 20%–100% (actually caps at ~92% due to the scale).

## Envelope group-delay equalizer

| Key | Effect |
|---|---|
| `g` | Toggle two cascaded first-order digital all-pass sections on the envelope path, fitted to flatten the *original* (non-Bessel) 2-pole Sallen-Key filter's group-delay dispersion — as of 2026-09-03, fit directly against a real-hardware TFA phase sweep over 100–8000Hz (was: LTspice sim, 100–4300Hz; see `ENV_GDEQ_A1`/`ENV_GDEQ_A2` in `envelope_gdeq.h` for the full derivation). Goal: get that filter's better stopband rejection without its dispersion-driven IMD penalty, instead of the Bessel filter's compromise. **Not yet IMD-validated on real hardware — see the dated entries below, including a correction to this project's own first same-day dispersion report.** |

Off by default. Enabling it pushes the envelope path's overall delay up by ~265µs (it can only add delay, not remove it) — re-tune `[`/`]` from scratch afterward; theoretical starting point is roughly **+2.65 samples**, a different regime from the Bessel filter's -0.20 to -0.25 samples.

**2026-09-03, `g` wired into the `'w'` chirp/sweep test path so the TFA can measure it directly.** `envelope_gdeq_process()` is now called unconditionally inside the `AUDIO_SRC_CHIRP` fast-path in `dsp_task` (`ssb_mic_test.ino`), in the same pipeline position as the normal full-tick path (before the offset/scale/predistort DC mapping) — it already no-ops internally when disabled, so no extra gating needed. Workflow: toggle `g`, press `'w'` to force an immediate fresh synced sweep (see next entry), read the TFA. Two bugs surfaced and were fixed getting here: (1) `serial_reply()`'s stack buffer (`char buf[256]`) was silently truncated by the longer `'w'` reply text once it grew to include `g`'s state — bumped to 512 bytes, reply trimmed to ~216 bytes, and a truncation warning added for future visibility; (2) `'w'` originally still guarded on `src != AUDIO_SRC_CHIRP` like every other source-select key in this file, so a second `'w'` press mid-sweep (needed for the A/B `g` workflow) did nothing — that guard was deliberately removed for `'w'` only (all other keys' guards untouched), so `'w'` now always restarts the sweep, even mid-sweep, on every press.

**2026-09-03, real-hardware TFA measurement (unwrapped phase, `g` off vs. on, sine-chirp sweep) — decisive gap from the LTspice-fit design prediction.** Phase data smoothed (Savitzky-Golay, window 31 ≈700Hz span, polyorder 3) before differentiating to group delay (`tau = -(1/360) dPhase/dFreq`). Over the design's own 100–4300Hz target band, at the currently-active config (`ENV_FILTER_VARIANT = ENV_FILTER_PNP_BC327_ATTN`, `SAMPLE_RATE_HZ = 16000`, i.e. `ENV_GDEQ_A1 = ENV_GDEQ_A2 = 0.622515`):

| | design prediction (`envelope_gdeq.h`, 2026-09-01 refit) | measured (this entry) |
|---|---|---|
| analog alone, p-p dispersion | 41.1µs | **146.1µs** |
| equalized, p-p dispersion | 13.7µs | **147.2µs** (essentially unchanged) |
| mean added delay | ≈131.6µs (2.105 samples @ 16kHz) | **≈40.3µs** (~31% of predicted) |

Sub-band breakdown (matters — the overall figure is not uniform across the band): 100–1000Hz shows a real, directionally-correct improvement (29.2→21.2µs p-p, ~28% reduction); 1000–2000Hz is flat (41.3→41.2µs); 2000–3000Hz shows a small improvement (69.0→66.5µs); 3000–4300Hz is flat-to-slightly-worse (146.1→147.2µs) and dominates the overall band figure since it's the widest and highest-magnitude sub-band. A residual-phase-noise check (raw phase minus the smoothed curve) shows RMS residual rising from ~0.4° at 100–1000Hz to a peak of ~2.5° at 3000–4300Hz — close to the analog filter's own corner, where attenuation is heaviest and measurement SNR is worst — so the apparent lack of correction specifically at the top of the band is confounded by degraded phase measurement there, not necessarily pure equalizer failure. No magnitude/coherence channel was captured in this measurement, so that confound can't be fully separated from a real equalizer shortfall with this dataset alone.

**Working interpretation (at the time):** the equalizer is doing *something* real and directionally correct at the low end of the band, but is well short of its LTspice-fitted design target overall, especially in the upper band where it was supposed to do the most work. **See the correction directly below — this interpretation turned out to be substantially a smoothing-window artifact, not a real equalizer failure at 100–4300Hz.** Raw TFA data: `Group_delay_off__on_F_Phase.txt` (user-supplied, tab-separated freq/phase, 'g' off then 'g' on, 0–24kHz).

**2026-09-03, CORRECTION to the entry above: the 31-point smoothing window was too fine for this real (noisier, denser) hardware sweep, and overstated the dispersion.** Prompted by a second request the same day: the user reported the TFA front end previously had a loading issue, now fixed by adding Hi-Z buffers, and asked for the compensation to be refit against the real data and extended to 8000Hz (`freq_dev_hz` excursions have been observed out to `MAX_FREQ_DEV_HZ`). Re-ran the SAME measured `g`-off/`g`-on curves (not a model — the actual measured phase in both states) at a wider window justified by a convergence check (stable from ~181 points/~4.2kHz span onward):

| Band | `g` off (measured) | `g` on (measured, then-active 0.622515/0.622515 coeffs) | |
|---|---|---|---|
| 100–4300Hz, 31-pt window (original entry above) | 146.1µs p-p | 147.2µs p-p | "no improvement" |
| 100–4300Hz, 181-pt window (this correction) | 36.6µs p-p | 14.3µs p-p | **real ~61% reduction, close to the 41.1→13.7µs LTspice prediction** |

So the *old* coefficients were doing close to what they were designed to do within their own 100–4300Hz fit band all along. The original "no improvement" finding above was substantially a smoothing-window artifact on noisy real data, not a genuine equalizer failure at those frequencies — left uncorrected above (not edited away) per this project's convention; this entry is the correction. This does **not** touch the separate, independently-confirmed 2026-09-01 real-hardware IMD result in `group_delay_fit_notes.md` (that measurement's repeatable delay-swept 3rd-order IMD numbers never depended on this phase-smoothing question) — only the group-delay/TFA read of things changes.

## Envelope pre-distortion

| Key | Effect |
|---|---|
| `D` | Toggle a measured-curve lookup table (`envelope_predistort.h`) that corrects the *static* (memoryless) nonlinearity of the whole envelope→RF-amplitude chain — PWM/RC filter, BS170 gate transfer curve, and the AD9851's own RSET-to-DAC-current relationship, all as one measured end-to-end curve. A different problem from `g`'s: this is amplitude vs. commanded level (present even with a constant carrier), not delay vs. frequency. **REPLACES** the `u`/`j`/`i`/`k` linear offset/scale mapping while on — those knobs have no effect until `D` is toggled off again. **Not yet validated beyond the measurement itself.** |

Off by default. Table derived from a real hardware sweep (single-tone + master-gain steps, PWM ranging at full 0–100% span) — see `envelope_predistort.h` for the full derivation and the curve's shape. Now on its 3rd revision: same 65 points, but rebuilt from an automated SDRuno logger's 363 dBm readings (0.1dB steps, -30dB to +6.2dB — far denser and wider-range than REVISION 2's 95 manually-read points over -16dB to +5dB), with the original 17-point gate-voltage curve kept but extended and spot-checked rather than re-measured (the automated logger can't read gate voltage — see `envelope_predistort.h`). Dead below ~30% duty, steep turn-on through ~30-55% (now wanting ~1-1.5 duty points more than REVISION 2 through most of that climb), then a gently-compressing climb that doesn't actually finish plateauing until ~98.8% duty, not the ~95% REVISION 2 assumed — REVISION 2's own top-end sweep wasn't quite dense enough to catch the last of it either, same class of miss as REVISION 1 had with the same region.

## Direct duty override

| Key | Effect |
|---|---|
| `d` | Toggle direct duty override on/off. While on, `dsp_task`'s normal envelope pipeline is locked out of the RSET output entirely (bypasses master gain, envelope, `u`/`j`/`i`/`k` offset/scale, AND `D`'s predistort LUT) — the LEDC hardware just holds whatever duty was last explicitly set below. Turning it on resets the working value to 0. Turning it off hands control back to the normal pipeline. |
| `>` | Step duty +1 count (finest resolution — only does anything while `d` is on) |
| `<` | Step duty -1 count |
| `N` | Step duty +16 counts (coarse) |
| `B` | Step duty -16 counts (coarse) |

Each step prints `-> duty NNN/1023`, same style as the `-> master gain ...` line. For characterizing the RSET/PWM/filter/AD9851 chain against a *known, exact* commanded duty count instead of one inferred from a gate-voltage reading — the reason this exists, see `envelope_predistort.h`'s REVISION 3 notes. The carrier/phase path is unaffected by this — select a steady source separately (`s`, single-tone, phase held rock-steady, is the natural choice — same as REVISION 1/2's own characterization used). Not yet used for a real sweep.

## Envelope-null floor

| Key | Effect |
|---|---|
| `x` | Raise the envelope-null floor by 0.02 |
| `z` | Lower the envelope-null floor by 0.02 (min 0.00) |

Two-tone envelopes dip toward zero at destructive-interference nulls, driving the commanded duty into the predistort LUT's steepest, most sparsely-characterized region (36–55% duty). `envelope_floor_apply()` (see `envelope_floor.h`) smoothly compresses envelope's whole `[0,1]` range into `[floor,1]` (peak still maps to 1, only the bottom is raised) so it can't be driven that low.

**Two earlier versions were tried and removed** — see `envelope_floor.cpp`'s header comment for both postmortems:

1. Also froze `freq_dev_hz` (phase rate) below the floor, meant to guard against `atan2()` noise near I=Q=0 — wrong for a two-tone signal (the fast phase rotation at a null is genuine required signal content, not noise) and produced a hard phase discontinuity: no effect until the floor got large enough (~0.08 in testing), then products jumping to 0dB right at that threshold as the accumulated phase debt snapped back.
2. A hard clamp (`min(envelope, floor)`) on the envelope side alone — left a derivative discontinuity at every crossing, which a two-tone signal hits often (near every null); showed up as nearly every product rising gently with each floor increment, a new distortion source confounding the actual question being tested. Replaced with the current continuous affine remap, which has no threshold and no kink anywhere in the trajectory.

Floor starts at 0.00 (off) — raising it trades some true-null carrier suppression (the deepest measured nulls only bought ~58dB anyway, see `envelope_predistort.h`) for keeping envelope out of the LUT's worst region. Applied unconditionally, right after `ssb_dsp_process_sample()`/the ENVSTEP/FMTEST/AMTEST equivalents, before `g`'s group-delay equalizer or `D`'s pre-distortion touch the envelope — so it sees the true raw signal, not a downstream-massaged version of it.

## freq_dev slew-rate limiter

| Key | Effect |
|---|---|
| `{` | Tighten the `freq_dev_hz` slew-rate limit (turns it on at 2000Hz/sample if currently off, then steps down 250Hz/sample at a time, floor 100Hz/sample) |
| `}` | Loosen the limit (steps up 250Hz/sample, then turns fully off past 8000Hz/sample) |

The phase-side counterpart to the envelope-null floor above — see `ssb_dsp.h`'s `ssb_dsp_set_freq_dev_slew_limit_hz()` doc comment for the full derivation. This limits how fast `freq_dev_hz` (the FM deviation fed to the AD9851 each sample) is allowed to *change* from one sample to the next — a different thing from `MAX_FREQ_DEV_HZ`, which limits its *value*. Verified numerically (a double-precision reimplementation of the exact DSP algorithm run alongside the real fast-math code, on synthetic two-tone input): real content, away from any envelope null, never asks `freq_dev_hz` to change faster than ~60Hz/sample even on busy high-center-frequency bands, while a genuine destructive-interference null asks for ~8000Hz/sample in a single step — a 100x+ gap with nothing in between. That single-sample swing is a real, correctly-computed requirement (it represents the true instantaneous phase reversal at the null), but a fast transient in frequency is inherently wideband in the spectrum. Limiting the slew trades a little reconstruction fidelity right at the null for less spectral splatter, without touching ordinary content.

Deliberately not a repeat of either envelope-floor mistake above: it doesn't freeze `freq_dev_hz` (no phase debt to snap back later — the AD9851 just integrates whatever frequency word it's handed each sample, so a slower-than-ideal ramp through the null *is* the applied modulation, not a deferred correction), and it isn't a hard value clamp (a slew limiter's output is continuous by construction, no derivative kink at any threshold). Applied inside `ssb_dsp_process_sample()`, after the `max_unclamped_freq_dev_hz` diagnostic captures the true unlimited peak and before the existing `MAX_FREQ_DEV_HZ` magnitude clamp (which still applies on top, unchanged).

Off by default (same convention as `g`/`D`/`x`/`z`) — not yet validated on real hardware beyond the numeric derivation above.

## Envelope output interpolation

| Key | Effect |
|---|---|
| `I` | Toggle 4x envelope output interpolation on/off |
| `C` | Cycle the interpolation curve: Catmull-Rom (default) -> linear -> HOLD (v4.4, no ramp) -> ... |

Right now the commanded PWM duty only changes once per DSP tick (`SAMPLE_RATE_HZ` = 16000) — a zero-order-hold staircase feeding the analog Sallen-Key reconstruction filter, whose first spectral image sits at 16kHz. Checked against the same real LTspice sweep behind `envelope_gdeq.h`: the filter only provides -27dB of attenuation at 16kHz, but -63dB at 64kHz — so linearly interpolating the envelope between DSP ticks up to 4x the update rate (64kHz) pushes that image out to where the filter actually buries it, +36dB "for free." Directly inspired by QRP Labs' QMX SSB firmware (see project history/`G0UPL.pdf`), which does the same thing (28x, driven by its own DAC/CPU constraints — 4x here is a deliberately modest first step, not a re-derivation of that number) and reported it eliminating visible overshoot/undershoot on the amplitude waveform entirely.

Implemented (v4, after three earlier real-hardware failures — see below) by speeding up the EXISTING sample timer itself to `ENVELOPE_INTERP_FACTOR` (4) x `SAMPLE_RATE_HZ` (64kHz), and only running the full DSP pipeline (Hilbert transform, atan2, sqrt, freq_dev, envelope, ADC, AD9851, diagnostics — everything) on 1 in `ENVELOPE_INTERP_FACTOR` of those wakes ("full" ticks, still true `SAMPLE_RATE_HZ` — every filter constant in the codebase keeps assuming that rate unchanged). The other 3 wakes just walk a linear-interpolation ramp between the last two full-tick envelope values and call the same plain `envelope_output_write_pwm()` the code always used. No second timer, no ISR, no extra task, no LEDC hardware fade — it all happens inside `dsp_task` itself, a single already-proven-safe FreeRTOS task on Core 0.

Took four attempts to land here, all from real-hardware failures, not simulation — recorded because each one rules out an approach that looks reasonable on paper: v1 (a second 64kHz `gptimer` whose ISR did the interpolation math *and* the `ledc_set_duty()`/`ledc_update_duty()` write directly) rebooted the ESP32 outright — general LEDC driver calls aren't guaranteed IRAM/ISR-safe. v2 (deferred just the write to a dedicated task, notified via `vTaskNotifyGiveFromISR`) still crashed, with a "Coprocessor exception" panic — the ISR still did the interpolation *arithmetic*, and on this chip's Xtensa cores the FPU is itself a coprocessor whose context only survives a *task* switch, so any float op in a true ISR is unsafe. v3 (moved the arithmetic into the task too, then rebuilt around the LEDC peripheral's own hardware duty-fade engine instead of any software timer) stopped crashing, but exposed two more problems in turn — a dedicated task waking 64,000 times/second on Core 1 starved `loop()`/`handle_serial_commands()` of CPU time; and once that was fixed via the hardware fade engine, the LEDC's free-running PWM clock (78125Hz, no integer relationship to `SAMPLE_RATE_HZ`) introduced ~12.8us of unsynchronized timing jitter per tick, visible as the envelope's effective frequency jittering. v4 (the user's own suggestion) sidesteps all of it by not using a second clock domain or extra task at all — `dsp_task` has always lived on Core 0, physically separate from `loop()`/Serial on Core 1, so running it faster carries none of v3's starvation risk, and there's only ever one clock. v4's own first cut still had a bug, found on real hardware EVEN WITH 'I' OFF (envelope timing jittery, IMDs shuffled up and down): it tracked "which of the 4 fast ticks is this" with a bare software counter incremented once per wake, but `ulTaskNotifyTake(pdTRUE, ...)` silently coalesces multiple real hardware ticks into one wake if `dsp_task` is ever even briefly late (a cache stall, a moment of contention) - at 64kHz that's a real possibility, and once it happens the counter permanently desyncs from the true hardware phase, so "full" ticks start firing at the wrong, irregular offsets indefinitely (a form of sample-clock jitter on the DSP rate itself). Fixed by using `ulTaskNotifyTake()`'s own return value (how many ticks actually elapsed, not just "at least one") to advance the counter, so it always equals the true cumulative hardware tick count and the phase can never drift. That fixed the OFF-state jitter, but the envelope still looked jittery with 'I' ON - a second, related bug (v4.1): the ramp itself was step-COUNTED (one `on_interp_tick()` call = one step), which is fragile against the exact same coalescing effect, now applied to the ramp - and it turns out to fire on almost every cycle, not rarely, because a full tick's own DSP processing (tens of us) is comparable to or longer than one fast sub-period (~15.6us), so 1-2 of the following interp ticks routinely elapse and coalesce away before dsp_task gets back to blocking, losing that many ramp steps by an amount that varies with exactly how long that tick's processing took - a real, structural, content-dependent source of jitter in the rendered envelope shape. Fixed by making the ramp time-BASED instead: each write computes its value directly from `esp_timer_get_time()` minus the true tick-start timestamp, divided by the sample period, rather than from a step count - so whatever calls DO happen (however many, however irregularly spaced) always land on the mathematically correct point on the ramp, and a coalescing event just means fewer visible steps that cycle, not a wrong value at the ones that do render. Still moving around after that (v4.2): the phase-lock fix only checked `fast_tick_count % ENVELOPE_INTERP_FACTOR == 0`, which assumes a coalescing event always lands EXACTLY on a multiple of 4 - it doesn't have to. If a full tick's own DSP processing occasionally takes long enough that MORE than 4 real periods elapse before `dsp_task` gets back to blocking, the count can jump straight past the next boundary (3 -> 8, skipping 4) - the modulo check then stays false until the count next happens to land exactly on a multiple, meaning that period's real DSP sample is skipped outright (a genuinely missing sample, not just a cosmetic ramp step), and the following full tick is delayed further still while waiting to re-land cleanly - compounding the original overrun instead of absorbing it. Fixed by comparing which `ENVELOPE_INTERP_FACTOR`-sized GROUP the count falls into rather than its exact remainder - any update that crosses one or more group boundaries is recognized as a full tick immediately, however far past the exact boundary a coalesced count landed, so a bad overrun still costs the one sample it made unrecoverable but can no longer cascade into delaying subsequent ones. Worth checking the existing `[timing]` diagnostic block's `overruns=`/`wakeup jitter: max_gap_us=.../late_ticks_total=` line - if those are climbing, `dsp_task`'s own per-tick processing time is what needs investigating next, separately from this counter logic. See `ssb_mic_test.ino`'s `dsp_task` and `envelope_interp.h` for the full design and failure history.

Off by default (same convention as `g`/`D`/`x`/`z`/`{`/`}`) — not yet validated on real hardware. **2026-08-31: real-hardware two-tone testing found `I` makes stability audibly *worse*, not better — a clear regression, not a subtle effect.** See `null_bias_investigation.md`'s item 5 (parked, higher priority than that document's own null-crossing-bias findings) — worth re-reading the v1-v4 failure history above first in case this is a fifth failure mode of the same kind, before assuming a connection to the separate null-crossing bias work.

**Curve, and `C` to switch it live.** The ramp between full-tick samples was originally a straight line (v4 above); `envelope_interp.h`'s own v4.2 revision replaced it with a Catmull-Rom cubic instead, validated offline against this project's own two-tone and AM-test envelopes before ever being flashed: ~23dB less interpolation error on the smooth AM-test envelope, but only ~2dB on the two-tone envelope specifically, because a two-tone null is a genuine derivative discontinuity (a local V-fold) that a smooth cubic structurally cannot reproduce — it rounds the fold off instead, where a straight line naturally can't do anything BUT reproduce a V. `C` (v4.3) makes that choice runtime-switchable for a direct A/B, without needing a reflash between them — see `group_delay_fit_notes.md`'s 2026-09-01 entries for why this became relevant (raised while chasing the new PNP BC327+attn filter's real-hardware IMD results). Both curves render over the exact same data window/timing (still the v4.2 4-sample/2-tick-latency pipeline) so switching `C` isolates curve SHAPE alone — no need to re-tune `relative_delay` between the two choices. Only affects output while `I` is ON; harmless to toggle with `I` off (remembered for next time `I` is enabled). Persisted per-preset as `envelope_interp_curve` (`settings.h`), defaulting to Catmull-Rom for every existing preset.

**Third curve, HOLD (v4.4) — isolates write RATE from ramp SHAPE.** `I` off vs on doesn't just add a ramp: with `I` off, `envelope_interp_on_interp_tick()` is a complete no-op, so the LEDC duty register is only written once per full DSP tick (`SAMPLE_RATE_HZ` = 16kHz effective PWM update rate). With `I` on — CATMULL_ROM or LINEAR alike — the register gets written 4x more often (64kHz), whatever curve is filling those extra writes. The Catmull-Rom-vs-linear comparison above only ever varied the SHAPE of that faster stream; it never isolated whether the faster write rate itself, independent of any ramp, is what matters. `C`'s third position, HOLD, answers that directly: it writes each full tick's value unchanged, 4 times, with zero added latency (unlike CATMULL_ROM/LINEAR, which both spend one tick "arriving" at the new value before settling). That gives a clean 3-way decomposition to A/B on the bench: `I` off (16kHz, once each) vs `I` on + HOLD (64kHz, same value repeated, no ramp) vs `I` on + CATMULL_ROM/LINEAR (64kHz, ramping) — isolating write rate from ramp shape instead of changing both at once. Same persistence/toggle rules as the other two curves (`envelope_interp_curve` in `settings.h`; harmless to leave selected with `I` off).

**2026-09-02, real-hardware result: HOLD raises the noise floor, both audibly and measured.** First bench use of the 3-way decomposition above found `I` on + HOLD produces a clearly higher and broader broadband noise floor than `I` off, heard directly and confirmed on a real-time FFT display (SDRuno, RBW 0.18Hz) — independently re-measured from the two capture screenshots themselves (pixel-brightness/lit-fraction of the off-peak skirt region, not just eyeballed): the HOLD capture ran ~30% more of that skirt area lit above threshold than the `I`-off capture, consistent across every off-peak sub-band checked, not a one-off artifact of a single frequency. Since HOLD writes a **bit-identical** duty value on all 4 of its per-tick writes, this rules out any explanation resting on the *value* changing — whatever is happening is triggered by the extra `ledc_set_duty()`/`ledc_update_duty()` calls themselves. Directly checked against the leading candidate mechanism (an LEDC internal latch-timing race, since `RSET_MOD_LEDC_FREQ_HZ`=78125Hz shares no integer relationship with the 64kHz write rate and the margin between the two is much tighter than at 16kHz): GPIO2 (`RSET_MOD_LEDC_GPIO`, the actual RSET/PWM line, pre-filter) scopes clean and equally well-behaved across `I` off, HOLD, LINEAR, and Catmull-Rom — no visible timing jitter or glitch on the commanded PWM waveform itself in any mode. That rules out a corrupted output waveform as the cause. Leading remaining hypothesis: digital switching/bus-activity crosstalk from the 4x-more-frequent register writes coupling onto some *other* node in the signal chain — the same category of effect as the confirmed `ADC_CONT_SAMPLE_FREQ_HZ`/`CHIRP_REF_GPIO`(pin13) crosstalk finding earlier this project, just now implicating the LEDC write path instead of the ADC driver. Not yet localized — next step is scoping the ADC input / audio chain or a ground/supply reference while toggling `I`/`C`, the same way the GPIO13 artifact was originally traced, to find where it's actually getting in.

**Correction, 2026-09-02 (same day): likely NOT an `I`-specific effect — retracted pending re-test.** Further bench work could not reproduce any `I`/HOLD-specific noise, and turned up a much bigger, better-explained cause instead (see "Sample rate (Fs) and dsp_task timing margin" below): at `SAMPLE_RATE_HZ`=16000 dsp_task is running with very little timing margin per tick, independent of `I` entirely. Worth also correcting the framing above: the fast-tick `gptimer` already fires at the full `ENVELOPE_INTERP_FACTOR`x rate (64kHz) **unconditionally**, regardless of whether `I` is on — see the sine-chirp test mode's own note in `config.h` ("the fast-tick infrastructure already runs unconditionally at 64kHz regardless of whether 'I' interpolation is toggled on"). So `I` off vs on was never "no wake-up at 64kHz" vs "wake-up at 64kHz" — dsp_task is woken at 64kHz either way; `I` only gates whether that wake's payload is a no-op or a few FLOPs + one register write. That's a small marginal CPU delta to hang a ~30%-more-lit noise floor on, which fits with it turning out not to reproduce. Most likely the two original screenshots simply landed on different sides of 16kHz's already-thin, already-variable margin, for reasons unrelated to `I`. Leaving the write-up above in place rather than deleting it (per this project's own convention of parking findings, corrections included) — the GPIO2-clean scope result is still valid and worth having on record either way.

**2026-09-02, settled: `I` left off (`ENVELOPE_INTERP_FACTOR` effectively x1) as the operating default, and `SAMPLE_RATE_HZ` back to 16000.** After the full HOLD/LINEAR/Catmull-Rom investigation above plus the separate factor 4/5/8 wake-rate sweep (below), real-hardware listening found no `I` setting — including x2, the mildest step up from off — that avoids an audible noise "burble" on tones, so there's no configuration where `I` provides its intended imaging benefit without a clearly audible cost on this hardware. Combined with the earlier `[timing]` margin findings (16kHz leaves ~16-17.5us of headroom vs 10kHz's ~55-58us) this closes out the interp/Fs investigation for now at the pre-existing, best-understood operating point: `I` off, `SAMPLE_RATE_HZ`=16000. Worth revisiting if the underlying mechanism (still unresolved — see the wake-rate-alone vs float-ramp-cost discussion above) ever gets pinned down and fixed.

## Sample rate (Fs) and dsp_task timing margin

**2026-09-02: reverting `SAMPLE_RATE_HZ` from 16000 to 10000 produced a dramatic, across-the-board improvement — bigger than anything `g`/`I`/`D` have shown so far, and it looks like the real explanation behind most of this session's noisier-than-expected real-hardware results.** Using Preset 1 (two-tone, `env_gdeq_enable`/`envelope_interp_enable` both off) and a mid-band noise test (0-3kHz broadband content relative to a 750Hz mid-band reference): at 16000Hz, -22dBc, and `D` (`env_predistort_enable`) made it 0.3dB *worse*. At 10000Hz: -32dBc with `D` off (a 10dB improvement from Fs alone) and -38dBc with `D` on (`D` now worth a genuine +6dB, instead of being net-negative). Frequency stability and the tone's subjective quality were both reported as noticeably better at 10kHz too. The tradeoff is real and expected: PWM/ZOH imaging is worse at 10kHz (closer first image, less filter stopband margin) — the whole reason `SAMPLE_RATE_HZ` was raised to 16000 and `envelope_interp`'s x4 output interpolation was built in the first place.

Why this is very likely a genuine timing-margin story, not a coincidence: `config.h`'s own `SAMPLE_RATE_HZ` comment already has the numbers. At 10000Hz (100us period), measured per-tick work (adc+dsp+write) was ~45us, leaving ~55us of margin — comfortably above the "~12-20us of wakeup jitter already measured" noted in that same comment. At 16000Hz (62.5us period), that same ~45us of work leaves only ~17.5us of margin — barely above that *same* 12-20us jitter figure, i.e. close to the exact threshold that got 20000Hz rejected outright in that comment ("period drops to 50us, leaving too little margin"). 16000 was picked as "the next value up from 10000 that still divides evenly," not because its margin was independently re-validated as generous — and on this data it wasn't. A tick that occasionally misses that ~17.5us window delays the next AD9851 frequency-word update, which is real, direct FM/PM timing jitter on the signal itself — a mechanism that would show up exactly as elevated broadband noise and worse frequency stability, and wouldn't touch `D`'s effectiveness directly (a static envelope-to-duty LUT correction has nothing to do with tick timing) except by being swamped underneath it, which is exactly the pattern seen (`D`'s benefit reappears once the swamping noise is gone at 10kHz).

**2026-09-02, `[timing]` captures at both rates (Preset 1, TWO-TONE, `I`/`g` off, `'r'` reset first):** at 16000Hz, `max_busy_us=46 (adc=4 dsp=20 write=28) period_us=62 overruns=0`, `max_gap_us=75 (nominal=62) late_ticks_total=0`. At 10000Hz, `max_busy_us=42 (adc=5 dsp=16 write=24) period_us=100 overruns=0`, `max_gap_us=107 (nominal=100) late_ticks_total=0`. Neither shows a formal overrun or late tick, so the strong "dsp_task is missing its deadline" framing isn't directly confirmed — but the margin actually available is: 16us at 16kHz vs 58us at 10kHz (matching the config.h estimate almost exactly), and the worst observed wake-gap excess eats ~80% of that margin at 16kHz (13us of 16us) vs only ~12% at 10kHz (7us of 58us). 16kHz is running close to its own edge even when nothing formally trips the overrun counter; 10kHz has a large cushion. Also notable: `[dsp] freq_dev: max_unclamped` dropped from 6697Hz (16kHz) to 3697Hz (10kHz) — consistent with `diagnostics.cpp` computing instantaneous frequency as `dphi * SAMPLE_RATE_HZ / (2*pi)`, meaning any *fixed* amount of phase-domain noise (quantization, ADC noise, Hilbert/atan2 rounding) gets scaled up proportionally by Fs before it ever reaches the AD9851 — a second, smooth, deterministic mechanism independent of scheduling jitter, plausibly worth a few dB on its own via FM-sideband scaling (~20*log10(16000/10000) ≈ 4dB).

**2026-09-02, `ENVELOPE_INTERP_FACTOR=7` at `SAMPLE_RATE_HZ=10000` — retracted, wrong fix for the wrong reason.** The idea (see the now-superseded item 4 this replaces) was to decouple the heavy pipeline's rate from the PWM output rate: keep the full pipeline at 10kHz for margin, but raise the interp factor so the envelope's PWM write rate could still reach ~70kHz for imaging. On the bench this brought the noise straight back to the same poor level as plain 16kHz. That result on its own looked like it might mean *wake rate itself* (not the full pipeline's Fs) was the real culprit — but a cleaner, fully-controlled follow-up test at a *fixed* wake rate ruled that out too, and points somewhere much more specific and useful:

**2026-09-02, decisive: it's not wake rate, it's floating-point ramp computation on the interp tick.** All four readings below are at the *same* wake rate — `SAMPLE_RATE_HZ=10000`, `ENVELOPE_INTERP_FACTOR=4` (40kHz), Preset 1, `D` on, mid-band noise test (`Pwr mid 750Hz band`, higher/less-negative = worse):

| Curve | Result | Δ from baseline |
|---|---|---|
| `I` off (baseline) | -35.4dB | — |
| `I` on, HOLD (no float math, frozen value) | -33.4dB | +2.0dB |
| `I` on, LINEAR (one multiply-add, changing value) | -23.9dB | +11.5dB |
| `I` on, Catmull-Rom (cubic Hermite, changing value) | -21.2dB | +14.2dB |

LINEAR sits far closer to Catmull-Rom (2.7dB apart) than to HOLD (9.6dB apart), despite being the much simpler of the two real curves — a single multiply-add vs a full cubic Hermite evaluation. That rules out "more arithmetic = proportionally worse": if raw operation count were the driver, LINEAR should land roughly midway between HOLD and Catmull-Rom, not almost co-located with the expensive one. What actually separates HOLD from both real curves is binary, not a matter of degree: HOLD never touches the FPU and always (re)writes the exact same frozen duty value; LINEAR and Catmull-Rom both do real floating-point work and genuinely change the commanded duty on every interp tick. Whichever of those two properties is the trigger, it looks like a step function at that threshold, not a smooth cost curve.

**Correction, 2026-09-02 (same day): the `ENVELOPE_INTERP_FACTOR=7` result is a SEPARATE bug, not the same mechanism as the table above.** Re-tested with `I` fully OFF at factor=7 (10000Hz base) — still -21.174dB, essentially identical to the factor=4 Catmull-Rom result (-21.181dB) despite the interp tick being a guaranteed no-op with `I` off. That rules out float-ramp cost or a changing duty value as the cause at factor=7 specifically, since neither happens with `I` off. The real cause: `init_sample_timer()` sets `resolution_hz = 2000000UL * ENVELOPE_INTERP_FACTOR` — 8MHz at factor=4, 14MHz at factor=7 — while `alarm_count` stays a fixed `2000000UL / SAMPLE_RATE_HZ` (200), computed assuming the requested resolution is achieved exactly. `GPTIMER_CLK_SRC_DEFAULT` on this chip is the 80MHz APB clock (same assumption this project's own LEDC comment already makes elsewhere). 80MHz/8MHz=10 is a clean integer prescaler; 80MHz/14MHz≈5.714 is not, so the driver silently rounds to the nearest achievable resolution — almost certainly 80MHz/5=16MHz (a +14.3% error), not the requested 14MHz. Confirmed directly: `[dsp] long-window avg=11371.71 ticks/s (13.717% vs nominal 10000Hz) true_ratio=7.0914 (nominal=8)` — a real, hardware-timestamped measurement (via `esp_timer_get_time()`, independent of the gptimer's own assumptions) showing dsp_task's actual full-tick rate running ~13.7% fast, matching the predicted +14.3% resolution error closely enough (small residual plausibly the ADC's own independent +0.8% clock error, plus measurement-window noise) to call this confirmed. At factor=4, this same diagnostic line has consistently read ~0.000-0.008% off nominal — 8MHz's clean divisor avoids the problem entirely.

Consequence: at factor=7, *everything* downstream of `SAMPLE_RATE_HZ` — the Hilbert/atan2 phase-to-frequency conversion (`dphi * SAMPLE_RATE_HZ / 2*pi`), the AD9851 write cadence, the ADC decimation ratio (`ADC_SAMPLES_PER_TICK` assumes an exact 80000/10000=8 relationship, and the diagnostic's own `true_ratio=7.09 (nominal=8)` shows that assumption is now wrong too) — is being computed against a `SAMPLE_RATE_HZ` constant that no longer matches the tick rate actually being delivered. That's a severe, systematic mistuning of the whole pipeline, entirely independent of `I`/curve choice, which is exactly why it showed up "even with `I` off." This has nothing to do with the HOLD/LINEAR/Catmull-Rom finding above — that one was cleanly demonstrated entirely at factor=4, a clock-clean rate, so it remains a real, separate, still-open question.

Two consequences for next steps: **(1)** the previously-proposed "factor=7 + HOLD" isolating test (see below) is now moot as a clean test of the compute-cost question, since factor=7 itself is broken for an unrelated reason — any result there would be confounded by this clock error, not informative about float-ramp cost. **(2)** if a higher PWM update rate than 40kHz is still wanted at `SAMPLE_RATE_HZ=10000`, pick a factor that divides cleanly: `80,000,000 / (2,000,000 * factor)` needs to be an integer, i.e. `40 / factor` needs to be a whole number — factor ∈ {1, 2, 4, 5, 8, 10, 20, 40} are clean (7 wasn't one of them), so factor=5 (50kHz) or factor=8 (80kHz) would be genuinely clock-accurate choices worth trying instead, once/if the separate compute-cost question below is resolved in a way that makes a higher factor worth having. Also worth fixing at the code level regardless: `init_sample_timer()` should read back the gptimer driver's *actually achieved* resolution (ESP-IDF's `gptimer_new_timer()` reports this) and derive `alarm_count` from that instead of assuming the request was granted exactly — that would make any future `ENVELOPE_INTERP_FACTOR` choice safe by construction rather than silently wrong for the "unclean" ones.

Two candidate mechanisms remain for the still-open HOLD-vs-LINEAR/Catmull-Rom finding (factor=4, clock-clean, so unaffected by the above), not mutually exclusive, both consistent with a step-function-at-threshold pattern rather than a smooth compute-proportional one:
- **CPU/scheduling:** the ESP32-S3's FPU is a genuine coprocessor (this project already hit that wall once, in the v1/v2 `envelope_interp` failure history — see above). If the *first* FPU touch after a context switch carries a fixed save/restore cost, any float ramp (LINEAR or Catmull-Rom) would pay roughly the same large fixed penalty per call regardless of how many operations follow, while HOLD's FPU-free path never pays it at all — matching the data far better than a compute-proportional story would.
- **Analog/RF:** HOLD's duty value is electrically static across all 4 of its per-full-tick writes — indistinguishable from `I` off except for redundant identical LEDC writes. LINEAR/Catmull-Rom genuinely move the duty (real switching-edge position change) on every interp tick, which could carry inherently more RF-relevant switching energy regardless of CPU timing — a real, expected cost of genuine modulation rather than a bug, and independent of anything CPU-side. The GPIO2 scope check from the (retracted) HOLD investigation found the PWM line "clean" across all curves — but that check has not yet been repeated specifically under this two-tone/Preset 1 content with a properly *dynamic* envelope; a near-constant test signal would hide exactly this effect since LINEAR/Catmull-Rom's ramp would have little to interpolate either way.

Not yet done, in order of how cheap they are: (1) re-scope GPIO2 comparing HOLD vs LINEAR/Catmull-Rom under this exact two-tone/Preset 1 condition at factor=4 (clock-clean), to distinguish the CPU-side hypothesis (would show timing jitter on the PWM line) from the analog/RF-side one (would show a clean but genuinely more-modulated waveform); (2) a lightweight timing probe directly around `envelope_interp_on_interp_tick()`'s curve branches (max/avg execution time per call, broken out by curve), to quantify the CPU-side hypothesis directly instead of inferring it.

**2026-09-02, item (3) done — HOLD itself degrades with wake rate alone, even with zero float math (curve state assumed, pending confirmation).** Re-tested `SAMPLE_RATE_HZ=10000` with the two remaining clock-clean factors above 4, presumed still on HOLD (this was the specific next step proposed above; not explicitly re-stated in the terse result messages, so treat as provisional until confirmed):

| Factor | Wake rate | Result | Δ from `I` off baseline (-35.4dB) |
|---|---|---|---|
| 4 | 40kHz | -33.4dB (HOLD, confirmed) | +2.0dB |
| 5 | 50kHz | -29.929dB (HOLD, assumed) | +5.5dB |
| 8 | 80kHz | ~-23dB (HOLD, assumed) | +12.4dB |

If the curve assumption holds, this is a clean, roughly monotonic degradation with wake rate alone — 40k→50k→80k — on a payload that never touches the FPU and rewrites the same frozen duty value every interp tick. That's a real, independent cost of high wake rate by itself, additive on top of the separately-confirmed (and larger, at a fixed rate) float-ramp/changing-value cost from the table above. It also **weakens the CPU/FPU-coprocessor-context hypothesis**: that theory predicted HOLD's FPU-free path should be largely immune to wake-rate scaling, but here it isn't. The analog/RF hypothesis doesn't fit cleanly either, since HOLD's duty value is static — redundant identical writes, not genuine modulation — so a third, more generic mechanism looks more likely now: something that scales with *ISR/wake frequency itself*, independent of what work happens inside each wake (e.g. fixed per-interrupt overhead — vector entry/exit, LEDC register write timing relative to the 78125Hz LEDC carrier repeating more densely, digital switching noise from the wake activity itself). This needs the curve state confirmed, and ideally isolated from the earlier float-ramp finding with a dedicated HOLD-only rate sweep at 4/5/8 run back-to-back in one session, before it's treated as settled.

**Interim recommendation:** leave `I` off, and if `I` is used, prefer the lowest clock-clean factor that gives useful imaging (4, i.e. 40kHz) rather than reaching for 5 or 8 to chase a higher PWM rate — both the float-ramp cost (fixed rate) and, provisionally, the wake-rate-alone cost (HOLD) get worse as factor increases, so there's no free lunch in going higher. At the most comfortably-margined case measured (`I` off, 40kHz-equivalent wake, 58us of headroom, zero overruns), `I` on still costs ~10-14dB even in its cheapest (HOLD, factor=4) form — an order of magnitude bigger than the "+36dB for free" imaging benefit it was built to capture ever needed to be weighed against, and bigger than any of `g`/`D`'s effects measured this session. Until the mechanism above is pinned down (and fixed, if it's addressable), `I` isn't paying for itself on this hardware.

## GPIO13 5kHz pulse — confirmed source: the ADC continuous driver

**2026-09-02, reported:** a regular short pulse on GPIO13 (`CHIRP_REF_GPIO`) at exactly 5kHz while in `'w'` (sine-chirp) test mode.

**2026-09-02, ruled out — not a software pin conflict.** GPIO13 is shared three ways in this codebase: `TIMING_DEBUG_GPIO_ADC` (adc_capture.cpp's ISR debug toggle, gated `ADC_ISR_DEBUG_PIN_ENABLED=0`), `TIMING_DEBUG_GPIO_CMD` (the `.ino`'s serial-activity marker, gated `CMD_DEBUG_PIN_ENABLED=0`), and `CHIRP_REF_GPIO` (the chirp mode's own intended square-wave reference output, unconditional). Checked every `#if` site touching this pin in `adc_capture.cpp` and the `.ino`: both debug-toggle paths are confirmed fully compiled out (single, unambiguous `#define`s, no override elsewhere in the project) — genuinely absent from the binary, not just runtime-disabled. So nothing in this project's own code was deliberately writing pin13 outside of the chirp reference toggle itself.

**2026-09-02, root cause identified: exact rate match to the ADC continuous driver's ISR.** `ADC_CONT_SAMPLE_FREQ_HZ / ADC_CONT_FRAME_SAMPLES = 80000 / 16 = 5000Hz` — precisely `adc_conv_done_cb()`'s own DMA-frame-completion firing rate (adc_capture.cpp), which runs continuously in every audio-source mode, chirp included, because `adc_capture_init()` is called unconditionally in `setup()` ("Always started now, regardless of the initial audio source"). Working theory: electrical coupling from the ADC continuous driver's real DMA/ISR activity onto the GPIO13 pad, independent of any code write to that specific pin — consistent with this project's own earlier, opposite-direction finding that driving GPIO3 digitally silently zeroed ADC conversions outright (config.h's "TRIED GPIO3 FIRST, REVERTED" note), which already established that GPIO1-10's digital activity and the ADC1 front-end aren't cleanly isolated on this chip. GPIO13 was deliberately chosen as ADC2 (unused by this project) specifically to get away from that — this suggests the isolation doesn't fully hold in the reverse direction either, plausibly because ADC1/ADC2 share analog reference/bias circuitry inside the SAR ADC block despite being logically separate units.

**2026-09-02, added `ADC_CAPTURE_ENABLED` (config.h, defaults to 1, no behavior change) as an isolation test.** Guards all three real call sites in the `.ino`: `adc_capture_init()` in `setup()` (skips starting the driver entirely — `adc_continuous_start()` is never called and the ISR never registers, not just a muted debug pin), `adc_capture_service()` in `loop()`, and the mic-source sample read in `dsp_task` (falls back to `sample = 0.0f`, matching the existing AMTEST/FMTEST/ENVSTEP "unused" convention). `diagnostics.cpp`/`serial_commands.cpp`'s ADC accessor calls were left unguarded — they only touch static state inside `adc_capture.cpp` and are safe to call with the driver never started (report zeros).

**2026-09-02, confirmed on real hardware: `ADC_CAPTURE_ENABLED=0` kills the 5kHz pulse on GPIO13.** Decisive — the ADC continuous driver's DMA/ISR activity is the source, not the chirp reference code, not a residual debug-pin write.

**Implication worth testing next:** the ADC continuous driver has been running at this same 5kHz ISR rate, unconditionally, through *every* mid-band noise measurement so far this session (two-tone mode included — the mic FIFO isn't drained in that mode, but the driver and its ISR are still live per the "Always started now" comment above). If this same coupling mechanism reaches the analog envelope/RF path the way it reaches GPIO13, it could be a constant background contributor sitting underneath the whole HOLD/LINEAR/Catmull-Rom and factor 4/5/8 noise-floor investigation above — present equally in every condition tested, so it wouldn't explain the *differences* between them, but it could explain part of why even the best `I`-off baseline (-35.4dB) isn't lower. Worth a quick check: rerun the mid-band noise test (Preset 1, `I` off, `D` on, two-tone) with `ADC_CAPTURE_ENABLED=0` and compare against the existing -35.4dB baseline — a rise (less-negative, quieter) would indicate the ADC driver is also coupling into the RF path itself, not just the digital GPIO13 line.

**2026-09-02, pin catalog and root-cause reclassification: this is a general ADC-pin-class problem on this board, not a GPIO13-specific one.** Cataloging every pin actually in use (`config.h`/`carrier_output.h`/`envelope_output.h`) against the S3's ADC1 (GPIO1-10) / ADC2 (GPIO11-20) channel map: GPIO2/4/5/6 (RSET PWM, the two timing-debug pins, mic) are ADC1; GPIO9/10 (`AD9851_PIN_RESET`/`_DATA`) are ADC1; GPIO11/12 (`AD9851_PIN_FQUD`/`_WCLK`) are ADC2; GPIO13 was ADC2. Every free pin on the board's main 1-13 header (1, 3, 7, 8) is also ADC1 — there is no non-ADC pin available there at all. Between GPIO3 (driving it digitally zeroed ADC1 conversions outright) and GPIO13 (receiving coupling from the ADC driver's own DMA/ISR activity), this project has now found real-hardware evidence of trouble in *both directions* across *both* ADC units on this chip — confirming Espressif's own guidance (ADC-183 errata: ADC2's digital/DMA controller is documented as unreliable; hardware design guidelines state "ADC1 is recommended for use") without needing to trust it blindly, since both directions are now independently reproduced on this exact board.

Flagged, not yet tested: **GPIO9-12 (the AD9851 bit-bang interface) are the strongest untested candidate for this same class of problem**, arguably more than GPIO13 ever was — they sit on both ADC units (9/10=ADC1, same unit as the mic; 11/12=ADC2), and unlike GPIO13's low-duty-cycle debug/reference role, they're the busiest digital lines on the whole board: DATA/WCLK/FQUD/RESET all bit-bang every full tick, already documented as the single largest `[timing]` line item (~24-28µs). Two distinct risk paths: (1) the same ADC-driver-coupling direction as GPIO13, but onto GPIO9/10 specifically — though this wouldn't reach the RF output in two-tone/chirp mode since those modes never read the ADC FIFO for signal content; (2) direct board-level crosstalk from these fast lines onto the nearby analog envelope/PWM output (GPIO2) or mic input (GPIO6), which doesn't go through the ADC's digital pipeline at all and would be live in *every* mode, RF-relevant regardless of test source. Not rewired — these are point-to-point wired to the physical AD9851 module, a materially bigger change than swapping a debug pin, so this needs bench evidence (scope GPIO6 grounded, or the GPIO2 PWM line, alongside AD9851's WCLK/DATA for an edge-correlated glitch) before it's worth disturbing a working interface.

**2026-09-02, moved `TIMING_DEBUG_GPIO_ADC`/`TIMING_DEBUG_GPIO_CMD`/`CHIRP_REF_GPIO` from GPIO13 to GPIO39.** Board is an ESP32-S3 Super Mini: GPIO1-13 on the main header (all ADC-associated, per the catalog above), GPIO39-48 reachable via small solder pads. Within that pad range, GPIO43/44 are the UART0 console (reassigning discouraged), GPIO45/46 are two of the S3's four strapping pins, GPIO47/48 are already wired to the I2C DAC (`MCP4725_SDA`/`SCL_GPIO`) — leaving GPIO39-42 (default hardware JTAG TCK/TDO/TDI/TMS, unused and safe to repurpose since this project debugs over USB CDC serial, not external JTAG). Picked GPIO39. No ADC channel on the S3, not a strapping pin, not the console UART, not already claimed — the first debug/reference pin on this board with no ADC association at all. Code updated (`config.h`, `ssb_mic_test.ino`, `adc_capture.cpp`, `serial_commands.cpp`, `settings.h`, `test_signals.h`) to match; not yet re-verified on the bench that GPIO39 is itself clean (should scope it the same way GPIO13 was scoped, now that it's carrying the chirp reference again).

**2026-09-02, reported and root-caused: GPIO39 read permanently LOW.** Real bug, not a wiring/board issue — `GPIO.out_w1ts`/`out_w1tc` (used at every raw-register toggle site in `adc_capture.cpp` and the `.ino`, chosen specifically for their ISR-safety/zero function-call-overhead) are only 32 bits wide and physically address GPIO0-31 only. `1UL << 39` doesn't hit a real bit in that register at all, so `GPIO.out_w1ts = (1UL << CHIRP_REF_GPIO)` for pin 39 was silently a no-op — not undefined/crashing, just quietly doing nothing, leaving the pin stuck at whatever `pinMode`/`digitalWrite(...LOW)` left it during `setup()` (that init call goes through Arduino's `digitalWrite()`, which *does* handle GPIO32+ correctly - only the hot-path raw-register toggles were broken). This was invisible with the pin at GPIO13 (<32, correct register) and only surfaced once the pin moved to GPIO39 (>=32) - a latent bug the GPIO13→GPIO39 move exposed rather than one it introduced.

**Fix:** added `GPIO_FAST_SET(pin)`/`GPIO_FAST_CLR(pin)` macros (`config.h`, right after `TIMING_DEBUG_GPIO_ISR`'s definition) that branch between `GPIO.out_w1ts/w1tc` (pin < 32) and `GPIO.out1_w1ts/out1_w1tc` at bit `(pin-32)` (pin >= 32) - the S3's second GPIO bank, needed for anything past GPIO31. Since every pin argument here is a `#define` constant, the branch folds away entirely at compile time (zero runtime cost, still IRAM/ISR-safe) - this can't silently break again the next time a debug/reference pin gets reassigned to something >=32. Replaced all three real call sites: `on_timer_alarm()`'s pin5 toggle (didn't need the fix, converted anyway for consistency), the chirp reference toggle (the one that was actually broken), and `adc_conv_done_cb()`'s pin toggle (currently compiled out via `ADC_ISR_DEBUG_PIN_ENABLED=0`, but fixed for correctness whenever it's re-enabled next).

**2026-09-02, build failure on first attempt: `GPIO.out1_w1ts`/`out1_w1tc` are anonymous unions, not plain integers, on this SDK (`esp32s3-libs 3.3.8`).** Real compiler error: `no match for 'operator=' (operand types are 'volatile gpio_dev_s::<unnamed union>' and 'long unsigned int')`, on both branches, even for the pin5 call site that never actually takes the `>=32` path at runtime - because both branches of the `if`/`else` still have to type-check at compile time regardless of which one a constant pin number folds to. `GPIO.out_w1ts`/`out_w1tc` (low bank) accept a bare assignment fine on this SDK (already proven, left untouched); `GPIO.out1_w1ts`/`out1_w1tc` (high bank) need the union's `.val` member - `GPIO.out1_w1ts.val = mask` instead of `GPIO.out1_w1ts = mask`. Fixed and left a comment explaining why the two banks are treated differently in the same macro, so it doesn't look like an inconsistency to a future reader.

## ADC / diagnostics

| Key | Effect |
|---|---|
| `f` | Cycle the ADC anti-alias low-pass filter: off → Butterworth → Chebyshev → off. Both are 4th-order (two cascaded biquads), same 3kHz -3dB point; Chebyshev trades a small in-band ripple (~1.4dB) for noticeably more stopband rejection above cutoff — see `adc_capture.h`/`ssb_adc_filter.h`. For A/B testing whether an artifact comes from the filter, and which filter family/order helps most |
| `v` | Mute/unmute the once-per-second `[timing]`/`[adc]`/`[dsp]` diagnostic block — mute this before adjusting other settings if you want to actually see the confirmation lines |
| `r` | Reset all diagnostic counters/watermarks for a clean measurement window (doesn't touch any of the settings above, only the stats) |
| `n` | Cycle the null-bias diagnostic's near-null envelope threshold through `{0.02, 0.05, 0.10, 0.20}` (starts at 0.05) — see the section below |

### Null-crossing frequency bias diagnostic (`[dsp] null_bias*`)

Added 2026-08-31 while chasing a two-tone "poor tone"/slow-drift/FM-noise complaint. Full derivation, method, and the confirmed measurement table live in **`null_bias_investigation.md`** — short version: `wrap_pi()`'s resolution of the ±π phase jump at each two-tone envelope null carries a small, deterministic, tone-pair-specific bias, and it's now measurable directly from firmware, no SDR needed.

Three lines print alongside `[dsp] freq_dev`, same ~1s cadence, gated the same way:

| Line | Fields | Use |
|---|---|---|
| `null_bias` | `f1`, `f2`, `expected_center` (`(f1+f2)/2`), `plain_mean`, `plain_bias` | `plain_bias` is a plain unweighted average — **confirmed wrong**, overstates the real effect by 2-3 orders of magnitude (100s of Hz vs. the real few-to-tens-of-Hz effect). Kept only for the mechanistic breakdown in `null_bias3`. |
| `null_bias2` | `weighted_mean`, `weighted_bias` | **The one that matches reality.** Envelope²-weighted average instantaneous frequency — the physically correct quantity (equals the power spectrum's centroid, a standard identity), confirmed against the SDR to within a few Hz across all six `TWOTONE_BAND_PRESETS` pairs. |
| `null_bias3` | `near_null_samples%`, `near_null_contrib`, `rest`, `threshold` | Diagnostic-only: how much of `plain_bias` comes from the small fraction of samples sitting right at a null (`envelope < threshold`) vs. everywhere else. Confirms the effect is localized to null crossings. |

Workflow to reproduce a reading: `T` to a tone-pair preset, confirm `e`/`c` (EQ/compressor) are off, confirm threshold reads 0.050 (press `n` to cycle back if not), `r`, wait ~1-2s, read the three lines. Counters reset via `ssb_dsp_reset_freq_dev_stats()` — same call `r` already makes, alongside `[dsp] freq_dev`'s `max_unclamped`/`clip_count`.

There's a compile-time check tying the array size to the `'0'`-`'9'` range (`settings.h`'s `static_assert`), so resizing it without updating `loop()`/`setup()`/`serial_commands.cpp`'s preset-select block — and the boot banner's own preset listing loop, which now reads the array size directly rather than a hardcoded count — fails the build instead of silently misbehaving.

## Current testing defaults (compiled in, before any preset is loaded)

- Two-tone mode on at boot
- EQ and compressor both off
- Master gain: -2dB
- Relative delay: 0 samples
- Envelope group-delay equalizer: off
- `MAX_FREQ_DEV_HZ`: 8000Hz. Originally raised from 2800Hz just to measure the real unclamped two-tone peak deviation (`[dsp] max_unclamped`, see `diagnostics.cpp`) while chasing a ~+100Hz two-tone frequency offset; that measurement came back ~4800-4900Hz — well above the old 2800Hz ceiling, meaning that clamp was routinely engaging on real signal peaks, not just as an edge-case safety limit. Separately, real-hardware mic white-noise testing showed the freq-dev clamp performs better set higher, so **8000Hz is being kept for now** rather than reverted to 2800Hz — not yet landed on a final permanent value. UPDATE 2026-08-31: `clip_count` reads 0 at every tone-pair/spacing tested at this clamp setting, which rules clamp-asymmetry out as the cause of the (much smaller, current-firmware) two-tone offset seen now — see `null_bias_investigation.md` for the mechanism that replaced this as the leading explanation.

## Quick workflow reminders

- Send `v` first if you're about to do fine-tuning — otherwise confirmations get buried in the 1-second diagnostic spam.
- Levels take a moment to settle on the spectrum analyzer after any change — wait before reading.
- `[timing]` line's `mode=` field tells you which signal source is actually active (goes through the same name mapping used for `t`/`s`/`p`/`y`/`h`'s own confirmation lines, so `ENVSTEP`/`FM TEST`/`AM TEST` show up correctly there too, not just `TWOTONE`/`SINGLETONE`/`mic`), and `gdeq=` tells you whether the group-delay equalizer was on during that measurement window.
- Recommended workflow for validating `g`: `p` (envelope step) with `g` off vs on, scope the RSET step edge directly — flatter group delay should show as a cleaner edge. Then `h` (AM isolation) with `g` off vs on, to check whether it has any effect on the still-unexplained AM-to-PM sideband asymmetry (-2.4kHz nulls out, +2.4kHz stuck at -40dB). Re-tune `[`/`]` (starting near +2.65 samples) before judging real two-tone/IMD results with `g` on.
- Empirically mapping envelope/phase delay mismatch vs. frequency (no lab equipment needed beyond the RF spectrum analyzer already in use): `T` to step to a band, `[`/`]` to find the delay that minimizes IMD/spurs for that band, capture a spectrum, repeat for the next `T` press. The resulting per-band "best delay" values trace out the actual (as-built) delay-vs-frequency curve, which can be fed back into refitting `ENV_GDEQ_A1`/`ENV_GDEQ_A2` against real measured data instead of the original LTspice simulation.
