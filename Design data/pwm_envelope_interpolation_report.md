# Envelope-Output Update-Rate Investigation: PWM/LEDC Findings

**Project:** ESP32-S3 Polar/EER SSB exciter (AD9851 phase path + PWM/RC amplitude path)
**Period covered:** through 2026-09-08
**Status:** Closed for now at the 16kFs baseline; DAC comparison (MCP4821) in progress as the next step.

## 1. Architecture

The exciter splits the SSB signal into phase and amplitude components (Polar/EER combining). The phase path drives an AD9851 DDS over SPI, updated once per DSP sample tick. The amplitude (envelope) path modulates the DDS's own RSET reference current through a BS170 MOSFET gate, driven by an ESP32 LEDC PWM channel and reconstructed to a quasi-DC control voltage through an analog RC/Sallen-Key filter. Modulating RSET this way scales the AD9851's output amplitude directly at the DDS, rather than modulating a downstream RF amplifier stage.

Because the two paths (phase and envelope) have different propagation delays through their respective processing and filtering, a relative-delay line (`'['`/`']'`) aligns them, and a group-delay equalizer (`'g'`) compensates the analog filter's own non-flat phase response — both built and tuned against this same PWM/RC output stage. A predistort lookup table (`'D'`) separately corrects a measured nonlinearity between commanded PWM duty and the resulting RF amplitude at the RSET/BS170 stage; that nonlinearity (and further work on it) is a distinct problem from everything in this paper, which is specifically about how fast and how cleanly the *digital* envelope value can be pushed out through the PWM stage.

The PWM (LEDC) output is fundamentally a duty-cycle average, only accurate as an analog envelope once low-pass filtered. Whatever rate the duty register is updated at sets a sample-and-hold (zero-order-hold) staircase, and that staircase's spectral image lands at the update rate itself. At the project's native sample rate (`SAMPLE_RATE_HZ`=16000Hz), the first image sits at 16kHz, where the existing analog filter provides only around -27dB of attenuation — not deeply buried. Relocating that image to four times the rate (64kHz) would put it in a much deeper part of the filter's stopband, worth roughly +36dB of attenuation "for free," matching a well-known technique from other SSB/EER projects (e.g. QRP Labs' QMX). This -63dB-at-64kHz projection is what motivated the entire interpolation effort documented below: update the PWM duty register four times per sample period (`ENVELOPE_INTERP_FACTOR`=4) instead of once, without changing the underlying 16kHz sample rate everything else in the DSP chain depends on.

## 2. Configurations tried

Five architectures were built and tested on real hardware, each replacing the last:

**v1 — direct ISR write.** A second 64kHz timer's ISR computed the interpolation and called the LEDC driver directly. Rebooted the chip immediately: the LEDC driver has no ISR-safety guarantee.

**v2 — deferred write, ISR arithmetic.** Kept the 64kHz ISR doing the interpolation math (floating point) and deferred only the register write to a task. Still crashed, with a coprocessor exception — the ESP32-S3's FPU is itself a coprocessor whose context only survives a task switch, so any float operation in true interrupt context is unsafe regardless of what happens with the result.

**v3 — dedicated task, then hardware fade.** Moved all the work (arithmetic and write) into a dedicated task, with the ISR reduced to an integer counter and a notify. This stopped crashing, but waking a task 64,000 times/second was enough overhead to starve `loop()`/serial input on the core it shared — the board stopped responding to commands entirely. Rebuilding around the LEDC peripheral's own hardware fade engine (`ledc_set_fade_with_step()`/`ledc_fade_start()`) removed the per-step software/task cost, but exposed a third problem: the LEDC's PWM clock (78125Hz, chosen only as the fastest achievable at usable resolution on the 80MHz APB clock) had no phase or frequency relationship to the 16kHz sample timer, so each fade's first step landed on an effectively random point in the PWM cycle — around 12.8us of unsynchronized jitter per tick, audible as frequency instability.

**v4 — single clock domain (long-standing default).** Rather than run a second clock domain at all, the existing sample timer itself was sped up to `ENVELOPE_INTERP_FACTOR` x `SAMPLE_RATE_HZ`, with the full DSP pipeline (ADC, Hilbert transform, AD9851 update, diagnostics) still only run on one in every `ENVELOPE_INTERP_FACTOR` ticks; the remaining ticks walk a software ramp (linear, later also a Catmull-Rom cubic) and issue a plain `ledc_set_duty()`/`ledc_update_duty()` write. This is architecturally the simplest of the five — one clock domain, no new ISR or task — and was the first version that didn't crash or starve the board outright.

Real-hardware measurement at a comfortably-margined base rate (`SAMPLE_RATE_HZ`=10000, `ENVELOPE_INTERP_FACTOR`=4, i.e. a 40kHz effective update rate) isolated two independent, additive costs:

| Configuration | Result (two-tone mid-band noise) | Δ vs. interpolation off |
|---|---|---|
| Interpolation off (baseline) | -35.4dB | — |
| On, HOLD (rewrite same value, no float math) | -33.4dB | +2.0dB |
| On, linear ramp | -23.9dB | +11.5dB |
| On, Catmull-Rom ramp | -21.2dB | +14.2dB |

HOLD's own small penalty was shown to scale with wake rate alone (40k/50k/80kHz gave +2.0/+5.5/+12.4dB), even with no floating-point work and an electrically static output — ruling out both "FPU cost" and "genuine RF modulation" as the sole explanation, and pointing instead at a generic cost tied to interrupt/wake frequency itself.

Separately, at the project's actual operating rate (`SAMPLE_RATE_HZ`=16000), raising `ENVELOPE_INTERP_FACTOR` to 4 caused an audible burble even with interpolation's *output* disabled (zero extra register writes) — confirmed, via the resulting shift in a synthesized test tone's own frequency, to be the DSP task genuinely missing its real-time deadline. The available margin at 16kHz (roughly 16-17.5us per 62.5us tick) is far thinner than at 10kHz (55-58us per 100us tick), and the same fixed per-wake overhead that 10kHz absorbs comfortably does not fit inside 16kHz's budget. This wake-rate-alone cost and the write/ramp cost from the table above are independent and additive.

**v5 — hardware fade revisited.** With the two mechanisms above characterized, the LEDC PWM carrier was retuned from 78125Hz to 64000Hz — an exact integer division of the 80MHz APB clock, and exactly `ENVELOPE_INTERP_FACTOR` x `SAMPLE_RATE_HZ` — on the theory that v3's original jitter came from an arbitrary, non-commensurate carrier rather than anything inherent to hardware fades. This retune alone was confirmed to build and run with no regression. v3's hardware fade engine was then reintroduced on top of it, with the sample timer and LEDC timer explicitly phase-synchronized at startup, and the cross-core wake to `dsp_task` throttled back to a genuine 16kHz (letting the LEDC hardware step the interior sub-ticks autonomously, with no CPU involvement at all).

The result was decisive and negative. A corrected two-part test (the first run was accidentally taken with interpolation disabled, which turned out to be informative in its own right) found: the bare 64kHz timer interrupt alone — with no fade engine engaged and no register write beyond the normal once-per-tick baseline — was on its own enough to reproduce most of the original burble, sharpening the earlier "wake-rate-alone" finding down specifically to the raw timer interrupt rather than the cross-core notification it carries. Separately, at a rate genuinely matched to the clean 16kHz baseline (so with the wake-rate cost controlled for), simply routing the same single write through the hardware fade API instead of a plain duty-register write produced real, audible degradation on its own. Engaging the fade engine at the full 64kHz rate combined both costs and was clearly worse than any earlier configuration, described on the bench as "completely destroys the two tones." The hardware fade engine was reverted; the commensurate-carrier retune was kept as a harmless residual change.

## 3. Sigma-Delta Modulation (SDM) — considered, not pursued

The ESP32-S3 has a separate Sigma-Delta Modulation peripheral, architecturally distinct from LEDC: its 1-bit output free-runs continuously at its own internal carrier (Espressif's own reference example uses 1MHz, roughly 15-20x LEDC's usable carrier ceiling), completely decoupled from how often software updates the target value. Because of this, it looked like it could sidestep every mechanism found above — a plain, ISR-safe register write once per 16kHz tick, with no interpolation architecture needed at all, since the quantization/image noise would already sit far out of band at the SDM's own carrier rate rather than needing to be pushed there by raising the software update rate.

It was not pursued, for two reasons. First, SDM's pulse density is only an 8-bit signed value (-128 to 127), with the vendor documentation recommending the usable range be kept to roughly ±90 of that (not the full span) for signal quality — a real cut in resolution and dynamic range relative to LEDC's already-in-use 10-bit duty, on a project that has already spent real effort fighting linearity and resolution limits elsewhere in this same signal path (the predistort LUT, the envelope-null-floor work). Second, it represents a substantial new implementation effort — a new peripheral to bring up, and the existing analog filter (tuned around the old PWM carrier) would need re-characterizing against SDM's very different spectral content — for an uncertain resolution outcome. Given a properly fast, genuinely DC-accurate SPI DAC (MCP4821) was a comparably-sized but much lower-risk alternative already under consideration, SDM was set aside in its favor.

## 4. Current state and conclusion

`ENVELOPE_INTERP_FACTOR` is left at its architectural default with the interpolation feature itself (`'I'`) off, i.e. the amplitude path runs at the plain, verified-clean 16kHz sample rate with a single PWM write per tick — no interpolation, no hardware fade. Every attempt to push the effective update rate higher (software ramp, LEDC hardware fade, at various sample-rate/factor combinations) ran into one or both of two independent, real costs on this hardware: a real-time margin ceiling in `dsp_task`'s own wake rate that is specific to running the full pipeline at 16kHz base (comfortable at 10kHz, thin at 16kHz), and a write/ramp-mechanism cost that exists even at a matched, uncontended rate. Neither was solved by any of the five architectures tried, including one (hardware fade) specifically designed to eliminate the first.

To be fair to what was actually built: the 16kFs, `ENVELOPE_INTERP_FACTOR`=1 configuration is a genuinely workable result, measured on real hardware at better than 30dB two-tone IMD suppression. The interpolation project did not deliver the additional imaging benefit it set out to capture, but it did not leave the exciter worse off than before the investigation began, and it closed out several real, previously-unexplained hardware behaviors along the way (a cold-boot i-cache warm-up stall, a starved diagnostic print line, an always-running ADC driver in non-mic modes) that are independent, useful findings in their own right.

## 5. Open items

A DAC comparison (MCP4821, 12-bit SPI, ~5us write-and-settle) is in progress as the next step, on the reasoning that a genuine instrumentation DAC removes the switching-carrier/duty-quantization issues inherent to PWM+RC entirely, independent of update rate. The AD9851/BS170 RSET-modulation AM distortion is a separate, already partially-addressed (via the predistort LUT) but not fully closed issue, tracked separately from this PWM/update-rate work.
